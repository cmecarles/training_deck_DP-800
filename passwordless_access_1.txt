============================================================
 SQL Server question — Passwordless Access 1
============================================================

Statement
---------

A motorway operator runs its toll-processing API as an AZURE
FUNCTIONS APP (Linux, .NET isolated) that reads and writes an
AZURE SQL DATABASE named TollGrid on the logical server
tollgrid-sql.database.windows.net. The security baseline says:

1. The application must connect WITHOUT ANY SECRET (no password,
   client secret, or connection-string key) in app settings, Key
   Vault, or source code.
2. The same code and the same connection string must work on a
   DEVELOPER LAPTOP (where the developer is signed in with az
   login) and in PRODUCTION in Azure, with no code branch per
   environment.
3. In production the Functions app authenticates as the
   USER-ASSIGNED MANAGED IDENTITY id-tollgrid-api, which is shared
   by two Function apps and must survive the recreation of either
   app.
4. The logical server has MICROSOFT ENTRA-ONLY AUTHENTICATION
   enabled (SERVERPROPERTY('IsExternalAuthenticationOnly') returns
   1), and a Microsoft Entra administrator is configured.
5. The identity must be able to read and write data only — it must
   not be db_owner.

Which configuration meets all five requirements?

a.

Create a SQL login tollapi with a strong password, store the
password in Azure Key Vault, reference it from app settings
(@Microsoft.KeyVault(SecretUri=...)), and use
Server=tollgrid-sql.database.windows.net;Database=TollGrid;User
Id=tollapi;Password=<from Key Vault>;Encrypt=True. In the
database: CREATE USER tollapi FOR LOGIN tollapi; ALTER ROLE
db_datareader ADD MEMBER tollapi; ALTER ROLE db_datawriter ADD
MEMBER tollapi;.

b.

Assign id-tollgrid-api to both Function apps. Connect with
Server=tollgrid-sql.database.windows.net;Database=TollGrid;Authentication=Active
Directory Default;User Id=<client ID of
id-tollgrid-api>;Encrypt=True (Microsoft.Data.SqlClient with
Microsoft.Data.SqlClient.Extensions.Azure). As the Entra admin run
in TollGrid:

CREATE USER [id-tollgrid-api] FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER [id-tollgrid-api];
ALTER ROLE db_datawriter ADD MEMBER [id-tollgrid-api];

Developers are added to an Entra group that has its own contained
user created with CREATE USER [sg-tollgrid-dev] FROM EXTERNAL
PROVIDER.

c.

Enable the SYSTEM-ASSIGNED managed identity on each Function app.
Connect with
Server=tollgrid-sql.database.windows.net;Database=TollGrid;Authentication=Active
Directory Managed Identity;Encrypt=True. As the Entra admin run
CREATE USER [func-tollgrid-api] FROM EXTERNAL PROVIDER; and add it
to db_datareader and db_datawriter. Because the identity is
created together with the app, no separate identity resource needs
to be managed.

d.

Register the API as a Microsoft Entra application and connect with
Server=tollgrid-sql.database.windows.net;Database=TollGrid;Authentication=Active
Directory Password;User
Id=tollapi@tollgrid.example;Password=<Entra
password>;Encrypt=True. Create the user with CREATE USER
[tollapi@tollgrid.example] FROM EXTERNAL PROVIDER; and add it to
db_datareader and db_datawriter. Because the account is an Entra
identity, the connection is compliant with Entra-only
authentication.

Correct Answer
--------------

b

Explanation
-----------

The question combines three things the exam expects you to keep
apart: WHICH CREDENTIAL TYPE (secret vs. token), WHICH IDENTITY
(system-assigned vs. user-assigned vs. human), and WHICH
CONNECTION-STRING AUTHENTICATION MODE selects the token
acquisition flow.

Requirement  | a (SQL login | b (UAMI + AD | c (SMI + AD  | d (Entra
             | + Key Vault) | Default)     | Managed      | user +
             |              |              | Identity)    | password)
-------------+--------------+--------------+--------------+-------------
1. No secret | VIOLATED (a  | satisfied    | satisfied    | VIOLATED
anywhere     | password     |              |              |
             | exists, just |              |              |
             | stored       |              |              |
             | elsewhere)   |              |              |
-------------+--------------+--------------+--------------+-------------
2. Same code | satisfied    | satisfied    | VIOLATED (no | satisfied
on laptop    |              |              | managed      |
and in Azure |              |              | identity on  |

-------------+--------------+--------------+--------------+-------------
3. Shared, a | n/a          | satisfied    | VIOLATED     | n/a
pp-independe |              |              | (SMI is per  |
nt identity  |              |              | app, deleted |

Why option b is correct
-----------------------

- PASSWORDLESS — a managed identity is a Microsoft Entra identity
  whose credentials are managed by the platform; the app obtains
  an access token for https://database.windows.net/ from the
  identity endpoint. There is no secret to store, rotate or leak.
  The Azure SQL documentation states it directly: "Managed
  identities for Azure resources eliminate the need to store
  passwords for services that connect to your databases".
- AUTHENTICATION=ACTIVE DIRECTORY DEFAULT makes the driver acquire
  the token with DefaultAzureCredential, which tries a chain of
  credential sources in order: EnvironmentCredential,
  WorkloadIdentityCredential, ManagedIdentityCredential,
  SharedTokenCacheCredential, VisualStudioCredential,
  VisualStudioCodeCredential, AzurePowerShellCredential,
  AzureCliCredential, AzureDeveloperCliCredential. In Azure the
  managed identity step succeeds; on the laptop it falls through
  to the Azure CLI (az login) token. One connection string, no
  environment-specific branch — exactly requirement 2. (The
  documentation warns that the chain adds connection latency; for
  strict SLAs prefer the targeted mode, but the question makes
  portability the constraint.)
- USER-ASSIGNED IDENTITY SELECTION — for a user-assigned managed
  identity "the Client Id of the User Assigned Managed Identity is
  read from the User Id connection property"
  (Microsoft.Data.SqlClient 3.0+; in 2.1 it was the object id).
  id-tollgrid-api is a standalone Azure resource, can be attached
  to several apps, and is NOT deleted when a Function app is
  recreated — requirement 3.
- DATABASE PRINCIPAL — CREATE USER [id-tollgrid-api] FROM EXTERNAL
  PROVIDER creates a contained database user mapped to the
  identity's object id (sys.database_principals.type = 'E',
  type_desc = EXTERNAL_USER); the name is the managed identity's
  display name. Only a Microsoft Entra principal with ALTER ANY
  USER — initially the Entra admin — can run it, because the
  engine validates the identity through Microsoft Graph.
  Membership in db_datareader/db_datawriter satisfies requirement
  5. Entra groups can be created as users the same way, which is
  how the developers get in.
- ENTRA-ONLY AUTHENTICATION — everything here is token-based, so
  it is allowed; SQL authentication is the only thing the setting
  disables.

Why option a is wrong
---------------------

Moving a password into Key Vault does not make the design
passwordless — a rotatable secret still exists, and requirement 1
forbids it. More decisively, requirement 4 kills it outright:
"When you enable Microsoft Entra-only authentication, you disable
SQL authentication at the server or managed instance level ... SQL
authentication users can't connect to the logical server ...
including all of its databases". You can still create tollapi (the
statement succeeds), but every connection attempt with User
Id/Password is rejected. The Key Vault reference is a distractor
aimed at people who equate "secret not in code" with
"passwordless".

Why option c is wrong
---------------------

Option c is the subtle one because it is a legitimate passwordless
pattern — Authentication=Active Directory Managed Identity (alias
Active Directory MSI) with a system-assigned identity is precisely
what the documentation recommends for "Azure-hosted workloads". It
fails the scenario, not the technology:

- A SYSTEM-ASSIGNED identity "is created as part of an Azure
  resource ... and shares the lifecycle of that resource" and "can
  only be associated with a single Azure resource". Two Function
  apps would need two identities, two database users, and
  recreating an app produces a new object id that orphans the old
  user — requirement 3.
- Active Directory Managed Identity only ever calls the
  managed-identity endpoint. On a developer laptop there is none,
  so the connection fails; developers would need a different
  connection string or code path — requirement 2.

Why option d is wrong
---------------------

Active Directory Password is Entra authentication, so it passes
the Entra-only check — that is the bait. But it is the ROPC
(RESOURCE-OWNER PASSWORD CREDENTIALS) flow: the app holds a user's
password in configuration (requirement 1 violated), it is
"incompatible with mandatory Microsoft Entra multifactor
authentication", and Microsoft has DEPRECATED it in the SQL
drivers (ActiveDirectoryPassword is [Obsolete] in
Microsoft.Data.SqlClient 7.0). The guidance is explicit: "Don't
use a Microsoft Entra user account as a service account"; use a
managed identity in Azure, a service principal (preferably with a
certificate) outside Azure, and Active Directory Interactive only
for humans present at sign-in.

What the database sees, and what SQL Server 2025 changes
--------------------------------------------------------

After CREATE USER [id-tollgrid-api] FROM EXTERNAL PROVIDER, the
principal is visible in the catalog with an external type; the SID
is the binary form of the identity's Entra object id, so you can
map it back:

SELECT name, type, type_desc, CAST(sid AS UNIQUEIDENTIFIER) AS EntraObjectId
FROM sys.database_principals
WHERE type IN ('E', 'X');       -- E = external user/app, X = external group

Two more details that show up as exam distractors:

- Azure RBAC roles such as SQL SERVER CONTRIBUTOR or SQL DB
  CONTRIBUTOR never grant database access — "Microsoft Entra
  authentication for Azure SQL doesn't integrate with Azure RBAC".
  The identity still needs a database principal and database
  permissions.
- The same passwordless pattern exists OUTSIDE AZURE: SQL Server
  2022 and SQL Server 2025 support Microsoft Entra authentication
  (default, managed identity, service principal, interactive/MFA,
  access token) once the host is connected to AZURE ARC (SQL
  Server on an Azure VM registers with the SQL IaaS Agent
  extension instead; on Windows a manual, Arc-less setup with
  certificates and an app registration is also documented).
  Failover cluster instances are not supported. The database-side
  statements (CREATE LOGIN ... FROM EXTERNAL PROVIDER, CREATE USER
  ... FROM EXTERNAL PROVIDER) are the same.

Conceptual question (Azure / tooling); not executed against an
engine.

DP-800 Exam Rule to Remember
----------------------------

"Passwordless" = token-based Entra auth with a MANAGED IDENTITY (or workload identity).
  Secrets in Key Vault / app settings = still a secret.  Entra user + password = ROPC, deprecated.

Identity choice:
  system-assigned  -> 1 per resource, dies with the resource, no cross-app sharing
  user-assigned    -> standalone resource, shareable, survives app recreation
                      (client ID goes in "User Id=" of the connection string)

Connection-string Authentication= values (Microsoft.Data.SqlClient):
  Active Directory Managed Identity | MSI -> only the managed-identity endpoint (Azure only)
  Active Directory Default             -> DefaultAzureCredential chain: env vars, workload
                                          identity, managed identity, VS/VS Code, Azure CLI ...
                                          (one string for laptop + cloud; slower to connect)
  Active Directory Interactive         -> humans, browser + MFA
  Active Directory Service Principal   -> app registration client id + secret/cert (outside Azure)
  Active Directory Password            -> deprecated, MFA-incompatible

Database side:  CREATE USER [<identity display name>] FROM EXTERNAL PROVIDER;  (run by an Entra
  principal, usually the Entra admin; contained user, type E/X; Azure RBAC roles do NOT grant
  database access).  Then ALTER ROLE db_datareader/db_datawriter ADD MEMBER ...
Entra-only authentication: disables SQL logins (they still exist, cannot connect);
  SERVERPROPERTY('IsExternalAuthenticationOnly') = 1; SQL Server 2022+/2025 gets Entra auth via Azure Arc
  (SQL IaaS Agent extension on Azure VMs; no failover cluster instances).
